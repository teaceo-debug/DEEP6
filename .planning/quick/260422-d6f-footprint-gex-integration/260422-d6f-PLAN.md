# DEEP6 Version Three — Footprint + GEX Integration Implementation Plan

> For Hermes: use subagent-driven-development for execution task-by-task once this plan is approved.

Goal:
Turn DEEP6 from a context-rich but partially ambiguous chart into a trade-decision system where:
1) footprint setups remain visible,
2) setup direction is explicit,
3) entry timing is explicit,
4) trigger timing is explicit without stop/target overlays,
5) GEX levels act as structural map / regime / target framework,
6) order-flow remains the execution trigger.

Architecture:
DEEP6Footprint remains the preserved legacy indicator. DEEP6FootprintV3 will own the Version Three setup lifecycle and setup/direction/trigger visuals. DEEP6GexLevels will own options-derived structural levels and publish them through shared state. Footprint scoring will consume GEX shared state at bar-close to create Armed trade setups only when footprint signals happen near meaningful GEX structure. Entries will trigger only on subsequent confirmation rules, not on the gray square itself.

Tech stack:
- NinjaTrader 8 / NinjaScript C#
- Existing DEEP6 detector registry + ConfluenceScorer
- Existing DEEP6GexLevels massive.com/Polygon-compatible fetch path
- New shared-state bridge for mapped NQ GEX levels
- NUnit tests under `ninjatrader/tests/`

---

## Product decisions captured in this plan

1. Gray square remains.
   - Meaning: setup/context marker only.
   - It is no longer the trade signal.

2. New trade lifecycle states.
   - Setup
   - Armed
   - Triggered
   - Invalid
   - Expired

4. Visual hierarchy.
   - gray square = setup detected
   - colored directional annotation = armed long/short bias
   - arrow = triggered entry
   - faded or crossed marker = invalid / expired
   - no stop/target overlays on the chart

4. Structural vs trigger roles.
   - GEX = where price should react / likely targets / regime boundary
   - Footprint = whether reaction is actually happening now

5. Initial trading logic.
   - Long setup: bullish absorption/exhaustion near Put Wall / supportive GEX node
   - Short setup: bearish absorption/exhaustion near Call Wall / resisting GEX node
   - Gamma Flip acts as regime boundary and frequent T1 target
   - No entry on setup print alone; must confirm on next-bar or retest trigger

6. Vendor strategy.
   - Current implementation remains based on DEEP6GexLevels output
   - Shared-state schema must be generic enough to support future TradeGex / Flash Alpha imports without changing footprint logic

## Acceptance criteria for the whole plan

1. Correctness
- scorer prior-bar bug is fixed
- barsSinceOpen is session-relative
- render no longer consumes mutable live nested bar structures
- rolling caches trim correctly

2. Footprint UX
- gray square remains as setup marker
- direction is explicit
- trade timing is explicit
- entry/stop/target are visible
- invalid/expired states are visible

3. GEX integration
- DEEP6GexLevels publishes machine-readable mapped levels
- DEEP6Footprint consumes GEX shared state for confluence, regime, and target selection
- stale GEX is handled explicitly, not silently ignored

4. Strategy semantics
- map (GEX) tells where to care
- footprint tells when to care
- trigger confirms when to act
- GEX provides likely target structure

5. Future-proofing
- TradeGex / Flash Alpha / other vendors can later map into the same shared-state schema without rewriting footprint logic

6. NinjaTrader compatibility gate
- every indicator-facing change must remain valid under NinjaTrader 8 / .NET Framework 4.8 patterns
- no new dependency may require APIs unavailable in NT8 host runtime
- every indicator file change must be verified by NT8 compile (F5 in NinjaScript Editor) before being considered done
- all new shared-state / scoring support files must remain NT8-API-free unless they intentionally live in indicator code

7. UI/UX gate
- chart must be understandable at a glance without reading the code or guessing from color alone
- setup marker, direction, trigger, stop, and targets must each have a distinct visual role
- the footprint cells must remain readable; overlays cannot drown the core order-flow information
- stale / invalid / expired states must be obvious and visually downgraded

## NT8 implementation constraints (mandatory)

1. NT8-safe code only
- Prefer BCL + NT8-supported .NET Framework 4.8 features.
- Avoid introducing modern runtime dependencies that only work in net8 test project.
- Shared-state helper classes should stay free of NinjaTrader imports unless they truly require host APIs.

2. Indicator lifecycle discipline
- Indicator changes must respect NT8 lifecycle boundaries:
  - `State.SetDefaults`
  - `State.DataLoaded`
  - `State.Realtime`
  - `State.Terminated`
- Device-dependent resources must stay in `OnRenderTargetChanged` / disposal paths.
- Cross-thread publishing must avoid UI-thread assumptions.

3. Verification required inside NinjaTrader
A change is not considered fully complete until it passes these host checks:
- F5 compile in NinjaScript Editor with zero compile errors
- indicator loads on a live or replay chart without freezing the chart
- no render exceptions / output-window spam from the new logic
- setup / trigger visuals render correctly in actual NT8 chart scaling modes

4. UI clarity rules
- Gray square = setup only
- Armed state = explicit directional wait label
- Triggered state = explicit BUY / SELL arrow
- stop and targets = persistent horizontal plan lines
- if a trader has to infer whether the system wants long or short from color alone, the UI has failed
